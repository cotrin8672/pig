# Remote Pairing：自分の別PCからpigの続きを開く

状態：Tauri版のUIなしバックエンドとCLIを実装。既定オフ。実行手順は
[リモート接続の使い方](remote-cli.md)。以下には初期のPoC結果と、購読UIなど今後の設計も含む。

### このPCで確認できた範囲

`cargo run --locked --manifest-path examples/remote-pairing-poc/Cargo.toml` で再現する。
iroh 1.5.0、Windows MSVC。同一プロセスに独立した鍵のEndpointを3つ作り、実ソケットで検証した。
ループバックUDP直結とローカルリレー強制（直接IP transportなし）を各6回実行し、全回で
未登録鍵の拒否、許可した鍵との固定データ往復、接続中の失効通知、同じ鍵の再接続拒否を確認した。
アプリ層の許可判定は接続確立後なので、失効は「QUIC接続を一切作れない」ではなく
「アプリのデータを返さず閉じる」を意味する。試験用リレーはループバック限定HTTPで、外側のHTTPS、
公開リレー探索、NAT越えは検証していない。登録は手動操作の代わりにメモリ上の許可鍵を指定した。

追加で `cargo run --locked --manifest-path examples/remote-pairing-poc/Cargo.toml -- --public-relay`
を実行し、irohの公開APリレー（`aps1-1.relay.n0.iroh.link`）を指定して同じ試験に成功した。
直接IP transportを無効化し、データ往復後にirohの経路情報でもリレーを確認した。
これはこのPCから公開リレーへの到達性の確認で、別回線の端末との直接接続・回線切替の検証ではない。

Windowsでは `cargo test --locked --manifest-path examples/remote-pairing-poc/Cargo.toml`
で再起動試験も実行する。隔離した2プロファイルを使い、登録・招待なしの再接続・解除後の拒否を
順に別プロセスで検証した。各プロセス内のホストとクライアントはループバックで実際に接続する。
鍵はユーザー単位DPAPIで保護し、鍵の欠損・破損で自動再発行しない。共用Windowsログインの
利用者同士を隔離するものではない。

## 完成時の操作

外出前、自宅PCのpigで招待を1枚発行し、パスワードマネージャーなどで自分に渡す。
研究室PCに着いたら招待を貼り付ける。発行が1台分の事前承認なので、両画面の同時操作は不要。
以後は研究室PCで「自宅PC」を選び、
自宅PCの既存チャットを開いて続きを送る。名前やIPではなく、登録した端末鍵で再接続する。
モデル、課金、拡張、ファイル、会話の正本は自宅PCに残る。ノートPCでのプロバイダーログインは不要。
自宅PCがスリープ・終了していればオフライン。初版では常駐化、オフライン送信、他人への共有、
モバイル、複数ホストの一覧統合は作らない。

## 調査結果と設計への反映

### Storybook の画面案（Settings → Remote Pairing）

統計と通知の間にリンク形の「Pairing」を置く。開いた画面では「このPCをホスト」と
「別PCに接続」を分け、自宅で招待を発行する操作と、外出先で使う操作を取り違えないようにする。
Story は模擬データのみで、待ち受けや端末登録は行わない。

- [Claude Code Remote Control](https://code.claude.com/docs/en/remote-control) は実行中のセッションを
  URL または QR から開ける。pig の招待は会話リンクではなく、端末に継続アクセスを許すものなので、
  「会話を開く」と「端末を登録」を別の操作にする。
- [OpenCode のペアリング](https://opencode.ai/docs/cli/web) は接続先をリンクや QR で渡せる。
  pig の初版は自分の Windows PC 間で、両端を同時に操作しない用途。QR の常設より、
  期限と使用回数を示した招待をコピーし、後で貼り付ける方式を優先する。
- [OpenCode のサーバー選択実装](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/app/src/components/dialog-select-server.tsx)
  は通常の一覧と追加フォームを同時に見せず、追加操作で切り替える。pig でも招待入力や権限の説明は操作時だけにする。
  開閉は既存の `snappy-motion.css` の折り畳みと同様に、見出しを固定して本文の高さを往復させる。

| 確認したもの | 設計に使う点 |
| --- | --- |
| [iroh Endpoint](https://docs.rs/iroh/latest/iroh/endpoint/struct.Endpoint.html)、[Router](https://docs.rs/iroh/latest/iroh/protocol/struct.Router.html) | Rust側で端末鍵を持つEndpointを作り、pig専用のプロトコル名（ALPN）だけ受ける。相手は接続で認証された公開鍵から識別し、本文の自己申告IDを信用しない。 |
| [N0 preset](https://docs.rs/iroh/latest/iroh/endpoint/presets/struct.N0.html)、[security & privacy](https://docs.iroh.computer/deployment/security-privacy) | 既定の探索はホームリレーの情報を公開する。中継でも本文はE2E暗号化されるが、接続メタデータは隠れず、直接接続の相手にはIPが見え得る。オフ時はEndpointを生成しない。 |
| [公開リレーの制限](https://docs.iroh.computer/relays/rate-limiting) | 試作は公開リレー。帯域・可用性の保証を置かない。正式配布を、無償リレーで何人でも使えるという仮定に依存させない。 |

| `apps/desktop/src/bun/client-hub.ts` | エラー・拡張UI・ターミナル等もローカル画面に配る実装。remoteを仮想ウィンドウとして追加せず、会話用に絞ったスナップショットと更新だけを送る。 |
| `apps/desktop/src/bun/{sdk-send-receipts,send-recovery-store}.ts`、[他ハーネスの復旧比較](harness-send-recovery-comparison.md) | pigには既に送信の受付台帳がある。「接続の復旧」「受付の照会」「新規送信」を分離する。新しいリトライキューやSDKを作らない。 |

## 境界とペアリング

```text
ノートPC：既存WebViewのリモート画面 → ローカルTauri
                                   ⇅ iroh（直接または中継、同じ端末認証）
自宅PC：Tauri（端末認証・失効）→ 専用IPC → Bun（操作の検証・会話の選択）→ SessionHost / pi
```

- **識別子は分ける。** 永続的な`EndpointId`はどの端末か、接続世代はどの接続か、
  pigの`hostId`/`epoch`はどの実行状態に対する操作かを表す。ウィンドウIDで代用しない。
- **招待は秘密の登録権限。** 使用前に漏れれば最初の所持者が自分の端末を登録できる。
  発行から12時間、1ホストにつき未使用1枚。再発行・取消で前の招待は無効。コピー文字列には
  版、ホスト公開鍵、256ビットの乱数を含む。接続先の公開鍵を照合してからトークンを送り、
  ホストは接続が認証した端末鍵の登録と招待の消費をSQLiteで同時にコミットする。
  保存するのはトークンのSHA-256だけ。使用後は招待取消ではなく端末登録の解除が必要。
  上記の発行・登録台帳は `apps/desktop/src-tauri/pairing` に実装。検証は
  `cargo test --locked --manifest-path apps/desktop/src-tauri/Cargo.toml -p pig-pairing`。
  接続との連携は通信PoCのみで、通常起動時の待ち受けや設定画面はまだない。
- **保存と失効。** Windowsではユーザースコープの[DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)
  で秘密鍵を保護し、Tauriのプロファイル別に保存。公開鍵の許可リストはホストが所有。
  秘密鍵・招待・会話本文を診断ログに残さない。鍵の読取失敗時は接続を停止し、黙って再発行しない。
  解除では許可を取り消してから既存接続・購読・未受付の処理を破棄する。既に受付済みのモデル実行は
  ローカルの会話に残り、失効しても取り消されない。端末を再登録すれば新しい接続世代になる。
- **初版の信頼単位は「自分の端末」。** 登録画面で、ホストの既存会話を閲覧できることと、
  送信を許すとホストのツールや課金が動くことを明示。ゲストに安全な閲覧リンクとは扱わない。

## データと異常系

1. **閲覧。** 初版の操作は会話一覧・会話を開く・購読解除。ホストが返した会話ハンドルから引き、
   リモートからの任意のファイルパスやcwdを受けない。会話本文・表示に必要な状態だけを型に列挙。
   ログイン、認証設定、端末操作、拡張UI、実行可能なウィジェット、画像・添付は転送しない。
   本文にユーザー自身が貼った秘密まで自動除去できる、という約束はしない。
2. **同期。** 選んだ会話の直近履歴＋基準リビジョンを返し、同じ購読の後続差分を適用する。
   初期取得と購読開始の間のイベントを落とさない。購読単位で欠落を判断し、ローカル全体の通番の飛びを
   そのまま欠落扱いしない。再接続・差分の欠落・遅い受信者には最新スナップショットで再同期。
   履歴は有界のページ、更新は有界のキューにし、上限超過は明示する。遅い端末でローカル画面を止めない。
3. **送信。** テキストの通常プロンプトだけを受ける。任意のRPC、シェル・スラッシュコマンド、
   拡張起動の入力経路へ流さない。通常プロンプトの結果としてのモデルのツール実行は別で、
   既存のホスト側ポリシーが適用される。承認待ちは状態だけを表示し、初版ではホストで回答する。
   ローカルと同時に送る場合も既存の受付ルールを通す。リモートの編集中の下書きはローカル画面に上書きしない。
4. **不明な結果。** 送信時点の`hostId/sessionId/epoch/requestId`と本文を固定する。
   応答だけ失ったら同じ送信のreceiptと会話を読む。ホスト再起動時も新しいIDで勝手に再送しない。
   確定不能なら「受付不明」と内容を残す。古い接続の遅延応答は新しい画面に適用しない。
5. **入力境界。** 専用プロトコル例`pig/remote/1`。長さを検査してからデコードし、種別、版、本文長、
   端末ごとの要求数・同時ストリーム数を制限。未知の操作は拒否。Rust→Bunで信頼元を明示し、
   リモートのバイト列を`pig_packet`やネイティブコマンドとして渡さない。
   失効・切断と受信済み要求の競合は、ホストで受付する直前にも接続世代を照合する。

## 実装順と合格条件

| 段階 | 差分 | 次へ進む条件 |
| --- | --- | --- |
| 0：実現性の確認 | TauriのRust側に最小の実験用Endpoint。SDK・通常プロファイル・本物の会話なし。iroh版を固定し、Windows MSVC、Rust最小版、依存、パッケージ増分を確認。 | LANと自宅回線＋テザリングで接続。直接とリレーの経路を診断情報で区別し、リレーのみでも配送できる。Windowsポータブル版で起動でき、機能オフ時に鍵作成・外部通信がない。 |
| 1：鍵と登録 | 設定に「端末を追加」「接続中」「解除」。Rustで鍵・招待・許可リスト・接続寿命を管理。まだ会話を送らない。 | 再起動後の再接続、未知の鍵、誤ったホスト、招待の期限・再利用・同時承認、接続中の解除に対するテスト。鍵・招待がログに出ない。 |
| 2：読み取り専用 | Bunに小さなremote用ハンドラ、Reactに接続先が明確なリモート画面。既存の会話表示部品を使い、ノート側の通常RPCにホスト操作を誤送信しない。 | 片方で模擬モデルが生成した応答を他方で追える。長い履歴、遅い端末、回線切替、サスペンド復帰、ホスト終了でもローカルを巻き込まない。設定・認証・他の配信が混入しない。 |
| 3：続きを送信 | 通常テキスト送信・受付照会を既存台帳につなぐ。送信先ホストを常に識別可能にする。 | 実機2台、別回線、隔離設定＋模擬モデルで送信。受付直後に切断してもSDK呼び出しは1回。ホスト再起動時に自動再送なし。両端の同時入力、失効、ローカル承認待ちも確認。 |

CIはローカルの2エンドポイントと隔離したBunホストで回し、必要な中継試験には制御可能なテストリレーを使う。
外部の公開リレー・テザリング試験は実機記録として分離する。`cargo test`、既存のBunテストと
Tauriポータブルsmoke、画面変更時は`pnpm test:ui`を実施。実機では経路、初回接続時間、
再接続時間、ストリーミング量と遅延を記録し、送信本文・鍵は記録しない。

**配布の判断：** 最初はTauri previewで既定オフ。製品版が別のパッケージング経路なら、
ワークフローやScoopを暗黙に切り替えない。公開リレーが遅い・到達できない回線での案内と、
実測に基づくリレー運用先を決めてから正式サポートを宣言する。
